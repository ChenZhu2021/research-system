# READMA

这是一个持续使用中的研究系统（Research System）。

它用于保存研究探索过程中形成的问题、理解、依据与关系，使这些内容能够在之后被重新找到、重新连接、重新解释，并与产品案例（Product Case）建立可追溯的联系。

这个 Repository 不是一个按主题分类存放研究文件的资料库，也不是一个已经完成理论体系的展示页。

我希望在这里保存的是探索本身：

- 问题如何被提出？
- 对象如何被区分？
- 理解如何发生变化？
- 新关系如何形成？
- 旧判断如何被重新解释或修正？
- 研究假设如何进入实践并接受检验？

### 这些问题是哪里开始的

它来自我自己在进行信息管理时观察到的一个现象：信息被保存下来，不等于理解被保存下来。

一段材料几年以后可能仍然存在，但当时为什么记录、它与什么问题有关、当时怎样理解、后来为什么改变判断，这些东西很容易消失。



这个观察逐渐变成了一个长期问题：：人在不断变化的理解中，怎样让过去的经验和材料仍然能够被重新看见、重新解释、重新建立关系，并最终参与新的判断和创造？系统在这个过程中应该帮助什么，又不应该替人决定什么？



围绕这个问题探索下来，这个问题逐渐被拆成了几个不同但相互关联的问题：

- 为了让未来重新理解成为可能，现在应该保存什么？
- 什么东西应该获得稳定身份，成为可以长期引用、修改和重新解释的对象？
- 哪些过去材料真的值得在当前活动中重新进入注意？
- 材料重新进入以后，关系怎样形成、检验、修改或拒绝？什么才真正构成新的理解？

这些问题后来分别进入了「为重新理解而设计」、Block、DES、创造 / 新理解等不同研究方向。



当 AI（23年的 chatGPT）出现后，我开始使用 ChatGPT 这类对话模型，AI 作为一个工具可以参与到总结、重组、提取线索、生成关系解释......以及其他很多其他过去主要依赖人的认知活动。

这件事促使我我开始研究 AI 背后的技术原理，这些研究让我意识到关于“过去的材料怎样重新参与理解”的问题，有新的实现可能。

AI 能够生成解释，并不意味着解释已经成立。这也使我更加关注：

- 系统可以参与认识过程到什么程度？  
- 什么只是机器提出的候选？  
- 什么仍然需要人的判断、确认和检验？



Agent 的出现进一步改变了这些问题的工程边界。

AI 不再只是解释一段文本，它开始：获得 context、读取历史状态、调用工具、修改真实对象，基于改变后的状态继续行动。

这让一些过去比较抽象的问题开始更具体：

#### （1）从“什么值得重新出现”到 Context Selection

“过去的什么材料，应该在什么时候重新进入当前活动？” 到了 Agent 环境里可以一步追问：当一个 Agent 持续执行任务时，它究竟应该获得哪些过去的信息作为当前 context？

#### （2）从 Block 到 Agent 的操作对象问题

“什么东西应该获得稳定身份，才能被长期引用、修改和重新解释？”到了 Agent 环境里，问题开始变得更加具体：当 Agent 开始持续修改真实工作内容时，它究竟是在操作什么？

这可能涉及 file、paragraph、retrieval chunk、具有稳定 identity 的 object，或者其他尚未被明确区分的操作单位。

**从“不覆盖过去理解”到 State / Provenance / Verification**：

“新的理解怎样不覆盖过去真正发生过的理解？”到了 Agent 系统里，它开始和一些具体问题发生连接：version、diff、rollback、provenance、verification......

比如：Agent 改了什么？基于什么依据？当时是什么状态？能不能恢复？一个判断是什么时候、基于什么条件形成的？

### 当前正在验证的

#### （1）DES

→ [DES](./product-cases/des/)

DES 当前主要验证的是 **Context Selection**：

- 大量的过往材料，什么真的值得在当前活动中重新进入注意？
- 进一步放到 Agent 场景里，就是：哪些过去的信息值得进入 Agent 当前的 context？



**这个问题不是“找到最相似的历史材料”。**



一个核心验证是：材料在表示上接近、材料之间可能存在关系、这种关系对当前活动有价值，以及这份材料此刻值得出现，并不是同一个判断。

其中，语义上的接近可以被关键词检索、向量检索等方法发现，但它不能直接说明两份材料之间存在有意义的关系，更不能直接说明这份材料此刻值得出现。

一些真实触动案例还让我开始观察另一种可能：有价值的重新连接是否有时并不来自语义相似，而来自表面内容不同、但关系结构或变化结构存在某种对应？

DES 当前主要通过真实触动案例和低干扰 collector 记录实际发生的情况，再以关键词检索、向量检索等方法建立基础基线，通过检索结果和 badcase 观察：机器容易找到的材料，与人在真实活动中认为“值得重新出现”的材料，到底在哪些地方相同，哪些地方不同？

#### （2）Block × Agent

Block 是我过去已经持续研究的问题之一：什么东西需要获得稳定身份，才能被长期引用、修改、重新组合和重新解释？

Agent 的出现让我重新回到这个问题。当 AI 不再只是读取和解释内容，而开始持续修改真实工作内容时，一个新的问题变得具体：Agent 实际上是在操作什么？

例如，一次修改可能落在：

- 一个完整文件；
- 一段文字；
- 检索过程中临时生成的片段；
- 某种具有稳定身份的对象；
- 或其他尚未被明确区分的操作单位。



目前这个方向仍处于问题形成和进一步拆解的阶段。

#### （3）GitHub Research System

这个 Repository 本身也是一个持续进行中的产品实验。

它探索的是：如果同一份研究材料会在不同时间、不同问题和不同实践中被重新解释，一个长期研究系统应该怎样保存这种变化？



因此，这个系统当前区分了几个主要的信息对象：

- 研究节点（Research Node）：保存某个时间真正形成的问题、观察、解释、判断或探索方向；
- 来源（Source）：在 Research Node 需要溯源、依据或原始语境时进入系统；
- 产品案例（Product Case）：研究进入真实实践并接受检验的地方。



系统当前遵循的一条重要原则是：后来重新理解一条旧 Research Node 时，不直接覆盖旧记录，而是创建新的 Research Node，并通过新的关系（Relation）记录这次重新理解。

Markdown 用来保存人能够阅读的研究语境。

YAML Frontmatter 用来保存程序可以确定性解析的身份（identity）、关系（relation）、来源（source）等结构化信息。



目前已经形成 Research System v0 信息模型，下一步是让真实历史材料进入系统，对 Research Node、Source、Relation 和 Product Case 的边界进行实际测试。

### 三条研究线目前的关系

DES、Block × Agent 和 GitHub Research System 目前的研究进展是不同步的：

- **DES**：已经形成一些明确的问题区分，正在通过真实案例、collector、retrieval baseline 和 badcase 进行验证；
- **Block × Agent**：目前处于问题形成和具体化阶段，尚未形成稳定判断；
- **GitHub Research System**：已经形成 v0 信息模型，正在从系统设计进入真实使用和压力测试。



目前值得继续观察、但还不能确认的问题包括：

- 三条研究线是否最终会形成某种统一的系统架构？
- DES 当前研究的上下文选择问题，是否会成为 Agent context 管理中的一个正式机制？
- Block × Agent 是否最终会形成某种稳定的 Agent 操作对象模型？
- Research System 当前形成的对象、历史与 provenance 模型，是否适合 Agent 的长期 state 或 memory？
- 三条研究线之间是否存在某种可以重复验证的连接方式？
- 它们是否最终需要进入同一个产品或系统？

### Repository Structure

当前 Repository 的最小结构为：

```text
/
├── README.md
├── current-focus.md
│
├── system/
│   └── model.md
│
├── research/
│   ├── nodes/
│   └── sources/
│
└── product-cases/
    ├── des/
    │   └── index.md
    │
    └── block-agent/
        └── index.md
```

其中：

- `README.md`：Repository 的总入口；
- `current-focus.md`：当前真正正在关注的问题空间；
- `system/model.md`：Research System 当前的信息模型与运行规则；
- `research/nodes/`：历史 Research Nodes；
- `research/sources/`：研究过程中实际需要引用和保存的 Sources；
- `product-cases/`：研究假设进入实践并接受检验的 Product Cases。
